1. Project Overview

This project turns AI usage tracking into a physical desk object: a small screen that always shows how close you are to your current session limit, weekly budget, reset timer, burn rate, and connection status.

Goal

Build a compact, always-on desk meter for Claude Code or other AI coding tools.

Design Doctrine

Local-first, cheap parts, no cloud dependency for the display, and no attempt to bypass platform limits.

Hardest Part

Not the screen. The real challenge is obtaining reliable usage data without depending on unstable/private behavior.

Policy-safe framing: this device should only display usage and diagnostics. It should not automate limit evasion, account rotation, scraping private dashboards, or bypassing service rules.

2. Bill of Materials

3. System Architecture

Use a two-part design: the computer does the usage collection and calculation, while the ESP32 only displays the normalized state. This keeps the firmware simple and lets you change data sources later without reflashing the device.

Core components

LayerResponsibilityFailure behavior

4. Device Protocol

Keep the protocol simple: one compact JSON payload every 10–60 seconds. The ESP32 does not need full history.

Canonical payload

{
  "schema": "ai-desk-meter.v1",
  "service": "claude-code",
  "current_percent": 50,
  "weekly_percent": 11,
  "current_reset_seconds": 4920,
  "weekly_reset_seconds": 547200,
  "burn_rate": "normal",
  "status": "Musing...",
  "mode": "active",
  "updated_at": 1760000000,
  "source": "local-provider",
  "confidence": "estimated"
}

Field meanings

FieldTypeMeaning
schemastringVersioned payload contract.
servicestringclaude-code, codex, gemini-cli, local-llm, mock.
current_percentnumber 0–100Current session/window usage estimate.
weekly_percentnumber 0–100Longer-period usage estimate.
current_reset_secondsintegerSeconds until current window resets.
weekly_reset_secondsintegerSeconds until weekly/monthly window resets.
burn_rateenumidle, low, normal, high, critical.
statusstringShort display message.
confidenceenumexact, estimated, mock, unknown.

Transport choices

Wi‑Fi MVP

ESP32 runs a small HTTP endpoint. Host posts JSON to /api/state. Easiest to debug in a browser.

POST http://device.local/api/state
Content-Type: application/json
BLE Product Mode

Host writes JSON bytes to a BLE characteristic. Cleaner desk setup, but pairing/debugging is more annoying.

Service UUID: 7b7e0001-usage-meter
State UUID:   7b7e0002-state-write

5. Firmware Spec

Firmware should be boring and durable. Its job is to render the latest state, handle connectivity, and avoid crashing.

Recommended firmware stack

Platform

PlatformIO or Arduino IDE with ESP32 core.

Graphics

Waveshare example driver first, then LVGL / LovyanGFX if needed.

JSON

ArduinoJson with fixed-size buffers.

Firmware state machine

StateScreenTrigger
BOOTLogo + hardware self-testPower on
PAIRINGDevice name + IP/BLE hintNo host configured
ONLINEUsage bars + reset timersValid payload received
STALELast data + “stale” warningNo payload for 90 seconds
OFFLINEWaiting for hostNo payload for 5 minutes
ERRORShort error codeBad JSON, transport failure, display error

Rendering rules

  • Refresh UI at 10–20 FPS max; usage values only need updates every few seconds.
  • Never block the render loop waiting for network data.
  • Use static allocation where possible.
  • Clamp all percentages to 0–100.
  • Display confidence: exact, estimated, mock, or unknown.
  • Use burn-rate color, not random animation speed, to communicate urgency.

Provider interface

class UsageProvider:
    name: str

    def read(self) -> UsageSnapshot:
        """
        Returns normalized raw usage data.
        Must never raise unhandled exceptions.
        Must include confidence: exact / estimated / mock / unknown.
        """

8. Enclosure and Physical Design

The fastest enclosure is a simple 3D printed frame with a rear wedge stand. Do not overbuild the first revision.

Case requirements

  • Front opening aligned to the display active area.
  • USB-C access on side or rear.
  • Vent slots near ESP32 module.
  • Rubber feet to stop sliding.
  • 5–15 degree viewing angle for desk use.
  • Optional rear cavity for battery only after USB version works.

Mechanical dimensions checklist

Measure your exact board before printing. Waveshare board revisions and clones can vary.

  • Board width measured
  • Board height measured
  • Board thickness measured
  • USB-C position measured
  • Button positions measured
  • Screen active area measured
  • Heat/vent clearance added

9. MVP Build Plan

Build it in small proof gates. The first useful version should not need BLE, battery, or a polished tray app.

Phase 1 — Hardware display proof

  1. Buy ESP32-S3 AMOLED board.
  2. Flash vendor demo.
  3. Confirm display, touch/buttons, USB logs.
  4. Draw static usage UI with hardcoded values.

Done when: the device shows a fake 50% / 11% screen without crashing.

Phase 2 — Wi‑Fi JSON proof

  1. ESP32 joins Wi‑Fi or creates setup AP.
  2. Host sends JSON to /api/state.
  3. ESP32 parses JSON and updates bars.

Done when: changing JSON on the laptop changes the physical screen.

Phase 3 — Host daemon proof

  1. Create Python CLI.
  2. Add mock provider.
  3. Add local config file.
  4. Add logs and test-payload command.

Done when: the host can run continuously and recover after device disconnects.

Phase 4 — Real provider

  1. Add provider abstraction.
  2. Use only official/local user-accessible usage sources.
  3. Mark confidence as exact, estimated, or unknown.
  4. Store last known state locally.

Done when: the meter reflects a real or honest estimated usage state.

10. Validation and Test Plan

This device needs boring reliability. It should never freeze just because the host app sends bad JSON or disappears.

Firmware tests

TestExpected result
Bad JSONReject payload, keep last good state, show error count.
Huge payloadReject safely; no crash or memory growth.
Wi‑Fi disconnectMove to stale/offline state.
Host stopsShow stale after 90 seconds, offline after 5 minutes.
Rapid payload spamRender latest only; do not queue endlessly.
Power cycleBoot to pairing or last config state cleanly.

Host tests

  • Provider returns missing fields.
  • Provider returns impossible percentages.
  • Device unreachable.
  • Network timeout.
  • Config missing or malformed.
  • Manual provider selected.
  • Mock provider demo mode.

Acceptance checklist

  • Screen readable from normal desk distance
  • Bars update from host JSON
  • Offline/stale state works
  • Bad payloads do not crash firmware
  • Host daemon logs useful errors
  • Confidence label visible for estimated data
  • Device can run for 8+ hours unattended

README positioning

# AI Desk Meter

A local-first physical usage dashboard for AI coding tools.

Supports:
- Claude Code usage display
- Mock provider for testing
- Wi‑Fi JSON transport
- ESP32-S3 AMOLED display target
- Extensible providers for Codex, Gemini CLI, local LLMs, and future tools

This project does not bypass usage limits. It displays available or estimated usage information.

12. Product Roadmap

v0.1 — Mock Meter

Static UI, mock data, Wi‑Fi JSON, no real usage provider.

v0.2 — Host Daemon

Python CLI, config, logs, mock/manual provider, payload validation.

v0.3 — Claude Provider

Local/official usage signal support with confidence labeling.

v0.4 — Product Shell

3D enclosure, OTA update support, better animations, docs.

v1.0 — Multi-AI Desk Meter

Claude Code, Codex, Gemini CLI, Ollama/local LLM usage, service switching.

v2.0 — Creator Kit

Printable case files, prebuilt firmware releases, setup wizard, merch/shop path.

Best market angle: do not make it only a Claude accessory. Make it a physical usage/status meter for AI coding tools in general.
